## Задание 3: «Ничего не забываем»

Проект доработан для промышленной эксплуатации с персистентным хранением в реляционной СУБД, управлением связанными ресурсами, контролем целостности, атомарными транзакциями и эволюцией схемы через миграции.

### Выполненные требования

1. **Реляционная база данных и персистентность (PostgreSQL 18 + Spring Data JPA):**
   - Все данные надежно сохраняются в реляционной БД. После перезапуска приложения накопленные данные сохраняются в неизменном виде.
   - Схема базы данных создается и валидируется **исключительно средствами Flyway**, автоматическая генерация Hibernate отключена (`spring.jpa.hibernate.ddl-auto=validate`).
   - Для развертывания PostgreSQL 18 подготовлен файл `docker-compose.yml`.

2. **Осмысленная связь между ресурсами и целостность данных:**
   - Между игроками (`Player`) и компьютерами (`Computer`) реализована связь `One-to-Many` / `Many-to-One`: один игрок может занимать компьютеры (до 1 для `REGULAR`, до 2 для `VIP`), а каждый компьютер в один момент времени закреплен максимум за одним игроком.
   - В таблице `computers` определен внешний ключ `occupied_by_player_id REFERENCES players(id) ON DELETE RESTRICT`.
   - Система блокирует любые ссылки на несуществующие ресурсы (возвращает `404 Not Found`).
   - Удаление связанных ресурсов не нарушает целостность: удаление занятого компьютера или игрока с активными компьютерами блокируется на уровне бизнес-логики и внешних ключей БД с кодом `409 Conflict`.

3. **Атомарная операция над несколькими связанными объектами (All-or-Nothing):**
   - Реализована операция пересадки игрока: `POST /api/computers/{id}/transfer` (с параметрами `targetComputerId` и `playerId`).
   - Метод аннотирован `@Transactional(rollbackFor = Exception.class)`.
   - Операция атомарно освобождает исходный компьютер и занимает целевой компьютер. Если целевой компьютер недоступен (уже занят, находится на ТО, либо категория компьютера VIP недоступна обычному игроку), выбрасывается исключение, транзакция полностью откатывается, и исходный компьютер гарантированно остается занятым.

4. **Эволюция схемы базы данных через миграции Flyway:**
   - `V1__initial_schema.sql` — создание исходных таблиц `players`, `computers`, внешних ключей и индексов.
   - `V2__add_hardware_specs_and_balance.sql` — содержательное изменение схемы:
     - Добавление колонок `ip_address` (VARCHAR) и `specs` (характеристики железа) в таблицу `computers`.
     - Добавление колонки `balance` в таблицу `players`.
     - Сохранение накопленных данных: автоматическое наполнение существующих компьютеров IP-адресами и спецификациями оборудования.
     - Создание уникального индекса `uq_computers_ip_address`.

5. **Исключение проблемы N+1 при выборке связанных данных:**
   - Эндпоинты `GET /api/players` и `GET /api/computers` возвращают подробную информацию о связанных объектах.
   - Выборка данных реализована через JPQL с `LEFT JOIN FETCH`:
     - `findAllWithComputers()` для загрузки игроков вместе с занятыми ПК за **один SQL-запрос**.
     - `findAllWithPlayer()` для загрузки компьютеров вместе с гостями за **один SQL-запрос**.
   - Поведение проверено тестом `ClubDatabaseTest.testFindAllWithComputers_noNPlusOneQueriesOnDozensOfEntities` на списке из 50 связанных сущностей с измерением количества выполненных JDBC-запросов через `Hibernate Statistics` (ровно 1 запрос).

6. **Тестирование:**
   - **Юнит-тесты доменной логики (`ClubServiceTest`):** 47 тестов, запускаются мгновенно без поднятия Spring-контекста, полностью изолированы и проверяют бизнес-правила и ограничения.
   - **Интеграционные тесты БД (`ClubDatabaseTest`):** 5 комплексных тестов на Spring Data JPA + Flyway, проверяющих сохранение связей, ссылочную целостность, откат транзакций и отсутствие N+1.

## Быстрый запуск

### 1. Запуск базы данных PostgreSQL 18
```bash
docker compose up -d
```

### 2. Сборка и запуск тестов
```bash
mvn clean test
```
или на Windows через скрипт:
```cmd
test.cmd
```

### 3. Запуск приложения
```bash
mvn spring-boot:run
```
или на Windows:
```cmd
run.cmd
```

### 4. Проверка API сквозными запросами (curl)
Скрипт содержит позитивные и негативные сценарии (400, 404, 405, 409):
```bash
chmod +x requests.sh
./requests.sh
```
Для PowerShell:
```powershell
.\requests.ps1
```
